# <Project> bible

How I (Main) run <Project>. Distilled from the owner's own words, most recent wins. Read it before every session and before briefing any lane; every lane brief says to read it in full. Project rules live in `<path>/AGENTS.md`; this file is how the work is run.

## 1. Direction

- What the project is, for whom, and what "done" means.
- Standing product decisions, each dated: (owner, YYYY-MM-DD).
- What never ships: compatibility shims, private material in public places, anything the owner ruled out.

## 2. Releasing

- The merge gate for a lane's tip (which tier, where it runs).
- The release procedure, step by step, with the exact commands.
- What counts as release evidence, and where it is recorded.

## 3. Roles and delegation

- Current lanes: name, area, worktree. Updated when a lane opens or closes.
- The approved lane cap.
- Where reviewer findings are saved.

## 4. Code rules

- The project's non-negotiables, beyond AGENTS.md. Each checkable rule has a lint rule or test behind it.

## 5. Tests

- What a test must exercise, what is banned, how long each tier takes.

## 6. Compute and the owner's machine

- Where heavy work runs, the memory caps, the scratch directories, the locks and their order.

## 7. Talking to the owner

- How the owner wants status, questions and reports.

## 8. Lessons (don't repeat)

- One line per mistake that cost time, with the date and the rule that now prevents it.

## 9. Standing authorizations

- What Main may do without asking: merges, deploys, pruning, answering specific prompts.
